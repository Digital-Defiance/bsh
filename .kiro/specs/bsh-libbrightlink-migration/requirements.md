# Requirements Document

## Introduction

The `bsh` shell ships a zsh module at `Src/Modules/brightlink.c` (1,963 lines) that implements the full BrightLink Protocol C client inline: the §4.5 LINK_REGISTER handshake, §4.6 LINK_DELIVER (AES-256-GCM AEAD with secp256k1 ECIES key exchange and HKDF-SHA256 derivation), and the §9 LINK_GEO_* verb family (STATUS, PROXIMITY, ZONE, GET, REFRESH). It exposes two zsh builtins on top of that: `bsh-inject` and `link-geo`.

The protocol code has now been extracted into a standalone canonical C library, libBrightLink (https://github.com/Digital-Defiance/libbrightlink, v0.1.0 preview at commit `3b84966`). The first consumer is the bsh-iputils suite (bping, btraceroute, etc.). bsh is the second.

This spec covers migrating the bsh module to consume libBrightLink instead of carrying its own copy of the protocol. The intent is purely structural: every byte of bsh's user-visible surface — the `bsh-inject` and `link-geo` builtin signatures, exit codes, and error messages — must remain bit-for-bit identical. The win is locality of bug fixes (one library, multiple consumers) and ~75% reduction in the module's source size.

A prerequisite: libBrightLink v0.1 only ships the LINK_REGISTER + LINK_GEO_GET surface (because that is all bsh-iputils needed). bsh needs the full surface (LINK_DELIVER, the four other LINK_GEO_* verbs, and LINK_PUSH for future subscribe support). So this migration includes extending libBrightLink to v0.2 with the missing verbs, in the upstream repo, before swapping bsh's module over.

## Glossary

- **bsh**: The shell at `/Volumes/Code/bsh/`, an independent fork of zsh that adds BrightChain integration. The build artefact is `Src/bsh`.
- **bsh module**: The dynamically loadable zsh module `bsh/brightlink` produced from `Src/Modules/brightlink.c`. Loaded into `bsh` via `zmodload`.
- **libBrightLink**: The canonical C client library for the BrightLink Protocol, currently a static library shipped as a git submodule at `subprojects/libbrightlink/` in each consuming repo. v0.1.0 preview at commit `3b84966`.
- **libBrightLink v0.2**: The version of libBrightLink that includes the full LINK_DELIVER, all five LINK_GEO_* verbs, and LINK_PUSH subscribe. Does not yet exist; this spec produces it.
- **BrightLink Protocol**: The wire protocol spoken between shell-side clients and the BrightNexus bridge. Specified in `docs/papers/brightlink.md` in the BrightChain monorepo. References §4.5, §4.6, §5, §9, §10 throughout this document refer to that document.
- **BrightNexus bridge**: The local Unix-domain-socket-bound daemon that terminates BrightLink Protocol connections. Out of scope for this spec.
- **bl_client_t**: The handle-based client object exported by libBrightLink (`include/brightlink/brightlink.h`). Replaces the bsh module's previous global static state (one socket fd + one K_session).
- **bl_pin_store_t**: The TOFU-pin-storage abstraction in libBrightLink. `bl_pin_store_memory()` keeps the pin in process memory only; `bl_pin_store_file(...)` persists it to disk.
- **bsh-inject**: The zsh builtin (currently `bin_bsh_inject` in `Src/Modules/brightlink.c`) that emits a `LINK_DELIVER` payload to the bridge. Used by the shell to deliver §5 schemas (command provenance, exit traces, audit records) to BrightNexus.
- **link-geo**: The zsh builtin (currently `bin_link_geo` in the same file) exposing the LINK_GEO_* verb family as `link-geo status | proximity <zone> | zone | get [--format ...] | refresh [--timeout N]`.
- **test-harness**: The vitest-based test suite at `bsh/test-harness/`. Comprises `against-real-brightnexus` (runs `bsh` against a real bridge), `against-real-bsh` (runs the JS reference against a real `bsh`), `against-real-client` (cross-validation), and `unit` (mock-driven). Used as the migration's behavior-equivalence oracle.
- **K_session**: The 32-byte AES-256-GCM session key derived during LINK_REGISTER and used to wrap LINK_DELIVER payloads. Currently held in module-global static storage; will move into the `bl_client_t` after migration.
- **§5 schema**: One of the payload schemas defined in BrightLink Protocol §5 that LINK_DELIVER may carry. `bsh-inject` currently emits the `command-context` shape with `dir_tag = 0x01` (Shell → Agent).

## Requirements

### Requirement 1: libBrightLink v0.2 Surface Extension

**User Story:** As a libBrightLink maintainer extending the library to support bsh, I want every BrightLink Protocol verb that bsh's existing module uses to be exposed through the libBrightLink public API, so that the bsh module can be rewritten as a thin glue layer without falling back to raw socket calls for any operation.

#### Acceptance Criteria

1. THE libBrightLink_v0_2 SHALL expose in `include/brightlink/brightlink.h` a `bl_deliver(bl_client_t *c, const char *type, const void *context, size_t context_len, const void *body, size_t body_len)` function returning `bl_status_t` that performs the §4.6 LINK_DELIVER round trip (AES-256-GCM wrap with §4.6.3 length-prefixed AAD, send to bridge, receive reply, decrypt) and that allocates and consumes the next per-direction monotonic counter (RFC §4.6.4) internally without requiring the caller to manage counter state.
2. THE libBrightLink_v0_2 SHALL expose a `bl_geo_status(bl_client_t *c, bl_geo_status_t *out)` function returning `bl_status_t` for the §9 LINK_GEO_STATUS verb, where `bl_geo_status_t` is a public struct declared in `brightlink.h` carrying at minimum the engine-alive flag, the last-fix BrightDate, and the fix-age-seconds value reported by the bridge.
3. THE libBrightLink_v0_2 SHALL expose a `bl_geo_proximity(bl_client_t *c, const char *zone_id, bl_geo_proximity_t *out)` function returning `bl_status_t` for the §9 LINK_GEO_PROXIMITY verb, where `bl_geo_proximity_t` is a public struct declared in `brightlink.h` carrying at minimum the boolean inside-zone result and the BrightDate at which the result was evaluated, and where a NULL or empty `zone_id` SHALL cause `BL_ERR_INVALID_ARG` to be returned without contacting the bridge.
4. THE libBrightLink_v0_2 SHALL expose a `bl_geo_zone(bl_client_t *c, bl_geo_zone_t *out)` function returning `bl_status_t` for the §9 LINK_GEO_ZONE verb, where `bl_geo_zone_t` is a public struct declared in `brightlink.h` carrying at minimum the current zone id (with the ownership and lifetime of that string documented in the header) and the dwell-time-seconds value.
5. THE libBrightLink_v0_2 SHALL expose a `bl_geo_refresh(bl_client_t *c, int timeout_seconds, bl_geo_position_t *out)` function returning `bl_status_t` for the §9 LINK_GEO_REFRESH verb that triggers a fresh fix and populates `*out` using the existing v0.1 `bl_geo_position_t` shape, accepting `timeout_seconds` in the inclusive range 1..300 and returning `BL_ERR_INVALID_ARG` for values outside that range without contacting the bridge.
6. THE libBrightLink_v0_2 SHALL expose a `bl_push_subscribe(bl_client_t *c, const bl_push_subscribe_config_t *cfg, bl_push_subscription_t **out)` function returning `bl_status_t` for the §10 LINK_PUSH subscribe entry point together with a `bl_push_unsubscribe(bl_push_subscription_t *sub)` function that cancels the subscription and releases the handle, where `bl_push_subscribe_config_t` is a public struct declared in `brightlink.h` carrying at minimum the topic identifier, a caller-supplied event callback, and an opaque user-data pointer passed back to that callback.
7. WHEN any v0.2 verb listed in criteria 1–6 is invoked on a `bl_client_t` whose LINK_REGISTER session is absent or expired, THE libBrightLink_v0_2 SHALL perform LINK_REGISTER lazily on the caller's behalf using the same handshake path as the existing v0.1 `bl_geo_get` lazy-register, and SHALL surface a register-time failure as the verb's own return status.
8. IF the bridge returns an `{"error": "..."}` envelope for any v0.2 verb OR a required pointer argument is NULL, THEN THE libBrightLink_v0_2 SHALL return `BL_ERR_BRIDGE_REFUSED` for the bridge-refused case and `BL_ERR_INVALID_ARG` for the NULL-pointer case, SHALL make the bridge's English error string available through `bl_last_bridge_error()` until the next call on the same client (bridge-refused only), and SHALL leave the verb's output struct (or `*out` push-subscription handle) in a fully-zeroed state with no partial population in either case.
9. THE libBrightLink_v0_2 SHALL set `BL_VERSION_MINOR` to `2` and `BL_VERSION_PATCH` to `0` in `include/brightlink/brightlink.h`, SHALL update `bl_version()` to return the resulting `"0.2.0"` string, and SHALL add a `CHANGELOG.md` entry that lists by name every newly added public symbol — functions, structs, typedefs, and enum tags — introduced by criteria 1–6.
10. THE libBrightLink_v0_2 SHALL preserve every v0.1 public function signature, struct layout, enum value, and macro value unchanged, with no removed symbols, no reordered or renamed fields on `bl_client_config_t`, `bl_client_config_v2_t`, or `bl_geo_position_t`, and no renumbering or repurposing of existing `bl_status_t` values; any new `bl_status_t` values introduced by v0.2 SHALL be appended after the v0.1 values.

### Requirement 2: Submodule Integration and Build System

**User Story:** As a bsh maintainer running `./configure && make`, I want libBrightLink to be discovered and linked the same way regardless of whether it is provided as a vendored submodule or a system-installed package, so that contributors on macOS, Debian, and CI all get a working build with one canonical command sequence.

#### Acceptance Criteria

1. THE bsh_repo SHALL declare libBrightLink as a git submodule in `.gitmodules` with `path = subprojects/libbrightlink` and `url = https://github.com/Digital-Defiance/libbrightlink.git`, with the gitlink in the bsh tree pinned to a single 40-character commit SHA on the `v0.2.x` branch recorded in the bsh commit that introduces the submodule.
2. THE bsh_configure SHALL accept a `--with-libbrightlink=ARG` flag where `ARG` is one of `submodule`, `system`, or `auto`, with `auto` as the default when the flag is omitted.
3. WHEN `./configure` runs with `--with-libbrightlink=auto` or `--with-libbrightlink=system`, THE bsh_build_system SHALL probe for a system libBrightLink first via `PKG_CHECK_MODULES([BRIGHTLINK], [brightlink >= 0.2])` and SHALL fall back to `AC_CHECK_LIB([brightlink], [bl_client_new])` plus `AC_CHECK_HEADER([brightlink/brightlink.h])` only if `pkg-config` is unavailable on the host.
4. WHEN `./configure` runs with `--with-libbrightlink=auto` AND the system probe in criterion 3 does not succeed AND the file `subprojects/libbrightlink/meson.build` is present and non-empty in the bsh source tree, THE bsh_build_system SHALL select the submodule build path; otherwise under `--with-libbrightlink=submodule` THE bsh_build_system SHALL select the submodule build path unconditionally.
5. WHEN the submodule build path is selected, THE bsh_build_system SHALL invoke `meson setup --buildtype=release --default-library=static <bsh-builddir>/subprojects/libbrightlink subprojects/libbrightlink` followed by `ninja -C <bsh-builddir>/subprojects/libbrightlink` from the `bsh/brightlink` module's Makefile fragment before the module's link step, and SHALL link the resulting `libbrightlink.a` into `Src/Modules/brightlink.so`.
6. WHEN `./configure` is invoked without the `--with-libbrightlink` flag, THE bsh_configure SHALL behave as if `--with-libbrightlink=auto` had been passed.
7. IF `--with-libbrightlink=submodule` is selected AND `subprojects/libbrightlink/meson.build` is missing or the submodule directory contains no files other than `.git`, THEN THE bsh_configure SHALL abort with a non-zero exit status and SHALL emit a diagnostic to stderr that names the literal command `git submodule update --init subprojects/libbrightlink`.
8. IF `--with-libbrightlink=auto` is selected AND neither the system probe in criterion 3 succeeds NOR `subprojects/libbrightlink/meson.build` is present, THEN THE bsh_configure SHALL abort with a non-zero exit status and SHALL emit a diagnostic to stderr that lists both the `git submodule update --init subprojects/libbrightlink` command and the option to install a system `libbrightlink` package providing `brightlink.pc`.
9. THE bsh_build_system SHALL prepend the include flag for the chosen libBrightLink headers (`-Isubprojects/libbrightlink/include` for the submodule path, or `$BRIGHTLINK_CFLAGS` from `PKG_CHECK_MODULES` for the system path) to the `bsh/brightlink` module's `CPPFLAGS` such that the flag appears before any other `-I` flag introduced by `Src/Makemod` or the module's own Makefile fragment, so that `#include <brightlink/brightlink.h>` resolves to the chosen libBrightLink before any other header search root is consulted.
10. THE bsh_configure SHALL remove the `AC_CHECK_LIB([crypto], ...)` and `AC_CHECK_LIB([secp256k1], ...)` invocations currently in `configure.ac` (around lines 858-869) that were added for the in-module protocol implementation, and the `bsh/brightlink` module's link line SHALL no longer pass `-lcrypto` or `-lsecp256k1` directly, since those are now transitive dependencies of libBrightLink.

### Requirement 3: User-Visible Behavior Preservation

**User Story:** As a bsh user who has scripts and aliases that invoke `bsh-inject` and `link-geo`, I want the migrated module to behave bit-for-bit identically to the pre-migration module on every input my scripts produce, so that I can pull the migration without auditing or updating any of my shell code.

#### Acceptance Criteria

1. THE migrated_bsh_brightlink_module SHALL register a `bsh-inject` builtin with the same `BUILTIN("bsh-inject", 0, ..., 0, -1, 0, NULL, NULL)` signature as the pre-migration module (`Src/Modules/brightlink.c` bintab entry).
2. THE migrated_bsh_brightlink_module SHALL register a `link-geo` builtin with the same `BUILTIN("link-geo", 0, ..., 0, -1, 0, NULL, NULL)` signature as the pre-migration module.
3. WHEN `bsh-inject --type <T> --context <C>` is invoked with the body bytes supplied on stdin (up to `LINK_BUF_MAX` bytes), THE migrated_bsh_brightlink_module SHALL produce a LINK_DELIVER request whose decrypted payload is byte-equivalent to the pre-migration payload for the same `(K_session, sessionId, counter, dir_tag=0x01, type=T, context=C, body)` tuple, and SHALL exit with status 0 on bridge acceptance.
4. WHEN `link-geo status` is invoked without `--json` and the bridge returns a non-error response, THE migrated_bsh_brightlink_module SHALL print to stdout, in this order, exactly the lines `alive: <v>`, `engine_kind: <v>`, `fix_age_seconds: <v>`, `accuracy_m: <v>`, each terminated by a single `\n`, and SHALL omit any line whose key is absent from the bridge response (matching pre-migration `link_geo_print_status` at `Src/Modules/brightlink.c` lines ~1644-1657).
5. WHEN `link-geo zone` is invoked without `--json` and the bridge returns a non-error response, THE migrated_bsh_brightlink_module SHALL print to stdout, in this order, exactly the lines `zone: <v>`, `dwell_seconds: <v>`, `brightdate: <v>`, each terminated by `\n`, omitting any line whose key is absent from the bridge response.
6. WHEN `link-geo proximity <zone-id>` is invoked without `--json` and the bridge returns a non-error response, THE migrated_bsh_brightlink_module SHALL print to stdout, in this order, exactly the lines `in_zone: <v>`, `brightdate: <v>`, each terminated by `\n`, omitting any line whose key is absent from the bridge response.
7. WHEN `link-geo refresh [--timeout N]` is invoked without `--json` and the bridge returns a non-error response, THE migrated_bsh_brightlink_module SHALL print to stdout, in this order, exactly the lines `fix_age_seconds: <v>`, `accuracy_m: <v>`, each terminated by `\n`, omitting any line whose key is absent from the bridge response.
8. WHEN `link-geo get [--format wgs84|brightspace|both]` is invoked without `--json` and the bridge returns a non-error response, THE migrated_bsh_brightlink_module SHALL print to stdout each present field as `<key>: <value>\n` in this fixed order: `lat`, `lon`, `alt_m`, `x_bm`, `y_bm`, `z_bm`, `accuracy_m`, `brightdate`, omitting any field absent from the response, and IF none of those fields are present THEN it SHALL print the raw bridge response followed by a single `\n` (matching `link_geo_print_position` at `Src/Modules/brightlink.c` lines ~1689-1735).
9. WHERE `--json` is supplied anywhere in the `link-geo` argument vector, THE migrated_bsh_brightlink_module SHALL print the bridge's raw response to stdout followed by a single `\n` and SHALL suppress all per-subcommand human-readable output, for both success and bridge-error responses.
10. WHEN any `bsh-inject` or `link-geo` invocation fails for any reason (transport error, bridge `{"error": "..."}` envelope, invalid argument, missing required argument, malformed flag value, LINK_REGISTER failure, LINK_DELIVER failure), THE migrated_bsh_brightlink_module SHALL exit with status `1`; on success it SHALL exit with status `0`. No other exit codes SHALL be produced.
11. IF a builtin invocation fails, THEN THE migrated_bsh_brightlink_module SHALL emit a single line to stderr of the form `<builtin-name>: <message>\n` produced by `fprintf(stderr, ...)` (NOT by zsh's `zerr`/`zwarnnam`/`error()`), where `<builtin-name>` is the `nam` argument passed to the builtin handler and `<message>` matches the pre-migration text for the same failure cause; in particular the following strings SHALL be preserved verbatim:
    - `unknown argument: <arg>` (bsh-inject, unrecognized flag)
    - `--type and --context are required` (bsh-inject, missing required flag)
    - `stdin read failed or exceeded <LINK_BUF_MAX> bytes` (bsh-inject, stdin overflow or I/O error; the literal numeric value of `LINK_BUF_MAX` SHALL match the pre-migration value)
    - `LINK_REGISTER failed: <reason>` (bsh-inject, registration failure)
    - `LINK_DELIVER failed: <reason>` (bsh-inject, deliver failure)
    - `bridge unavailable` (link-geo, transport failure on any subcommand)
    - `no response from bridge` (link-geo, empty/NULL response)
    - `unknown subcommand: <sub>` (link-geo, unrecognized first positional)
    - `proximity requires a zone id` (link-geo, missing zone arg)
    - `zone id too long` (link-geo, zone arg length > 256)
    - `--format must be wgs84, brightspace, or both` (link-geo get, invalid `--format` value)
    - `--timeout must be 1..300` (link-geo refresh, non-numeric or out-of-range `--timeout` value)
    - `<subcommand>: <bridge-error-text>` (link-geo, bridge `{"error": "..."}` envelope, non-`--json` mode)
12. WHEN `link-geo` is invoked with no arguments (`argv[0] == NULL`), THE migrated_bsh_brightlink_module SHALL print to stderr the same multi-line `Usage: <nam> <subcommand> [args...]` banner as the pre-migration module (subcommands list including `status`, `proximity <zone-id>`, `zone`, `get [--format wgs84|brightspace|both]`, `refresh [--timeout SECONDS]`, and the `--json` common flag) and SHALL exit with status `1`.
13. THE migrated_bsh_brightlink_module SHALL accept and reject the same argument vectors as the pre-migration module for both builtins, with the following preserved edge cases: (a) `bsh-inject` rejects any token not matching `--type` or `--context` with `unknown argument`; (b) `bsh-inject` requires both `--type` and `--context` regardless of order; (c) `link-geo --json` is honored at any position in argv (stripped before subcommand dispatch); (d) `link-geo get` defaults `--format` to `wgs84` when the flag is absent; (e) `link-geo refresh` defaults `--timeout` to `30` seconds when the flag is absent; (f) `link-geo refresh --timeout V` rejects any `V` for which `strtol` does not consume the entire token or whose value is `< 1` or `> 300`; (g) `link-geo proximity` with a zone id of length `> 256` is rejected before any bridge contact.
14. WHILE the `BRIGHTNEXUS_SOCKET` environment variable is set to a non-empty value at builtin invocation time, THE migrated_bsh_brightlink_module SHALL use that path as the BrightNexus bridge Unix-domain-socket address; otherwise it SHALL fall back to `$HOME/.brightchain/brightnexus/brightnexus.sock`, matching the pre-migration resolution order at `Src/Modules/brightlink.c` lines ~267-282.

### Requirement 4: Module Source Size and Glue-Only Scope

**User Story:** As a bsh maintainer reviewing the post-migration `Src/Modules/brightlink.c`, I want every line in the file to be either zsh module plumbing, builtin argument parsing, or a thin call into libBrightLink, so that nothing in this file overlaps with code that already lives in the canonical library.

#### Acceptance Criteria

1. THE migrated_bsh_brightlink_module SHALL contain no function definition, macro expansion, or inline body that implements the LINK_REGISTER, LINK_DELIVER, LINK_GEO_STATUS, LINK_GEO_PROXIMITY, LINK_GEO_ZONE, LINK_GEO_GET, LINK_GEO_REFRESH, or LINK_PUSH wire exchange beyond a single call to the corresponding libBrightLink public function (`bl_register`, `bl_deliver`, `bl_geo_status`, `bl_geo_proximity`, `bl_geo_zone`, `bl_geo_get`, `bl_geo_refresh`, `bl_push_subscribe`).
2. THE migrated_bsh_brightlink_module SHALL define no symbol whose name begins with any of the prefixes `link_aes_`, `link_gcm_`, `link_hkdf_`, `link_ecies_`, `link_secp_`, `link_b64`, `link_build_transcript`, `link_build_deliver_aad`, `link_verify_p256_`, `link_register_`, `link_emit_`, `link_pinned_`, or `link_pin_`, and SHALL contain no `#include` of any header under `<openssl/...>` or `<secp256k1*.h>`.
3. THE migrated_bsh_brightlink_module SHALL define no symbol whose name begins with `link_socket_`, `link_resolve_socket`, `link_send_request`, `link_write_all`, or `link_read_until_brace`, and SHALL contain no direct call to `socket(2)`, `connect(2)`, `bind(2)`, `send(2)`, `recv(2)`, `sendmsg(2)`, `recvmsg(2)`, `read(2)`, or `write(2)` against a bridge file descriptor.
4. THE migrated_bsh_brightlink_module SHALL define no symbol whose name begins with `link_json_` and SHALL contain no hand-rolled JSON tokenizer, parser, or serializer; the only JSON-shaped string handling permitted is (a) passing builtin arguments through to libBrightLink call parameters and (b) printing fields from libBrightLink return structures to stdout via the per-subcommand `link_geo_print_*` helpers and the equivalent `bsh-inject` stdout path.
5. THE migrated_bsh_brightlink_module SHALL include `#include <brightlink/brightlink.h>` and SHALL NOT include any header from the `subprojects/libbrightlink/src/` tree, any header named `brightlink_internal.h`, or any header under a `libbrightlink/internal/` path; the only libBrightLink symbols the module may reference are those declared in the public header `<brightlink/brightlink.h>`.
6. THE migrated_bsh_brightlink_module SHALL retain, with their pre-migration names and zsh-expected signatures, the entry-point functions `setup_`, `features_`, `enables_`, `boot_`, `cleanup_`, and `finish_`, the `static struct builtin bintab[]` table containing exactly two `BUILTIN(...)` rows for `bsh-inject` and `link-geo`, the `static struct features module_features` aggregator, and the `#include "brightlink.mdh"` and `#include "brightlink.pro"` zsh-module-build directives.
7. THE migrated_bsh_brightlink_module SHALL retain the `bin_bsh_inject` and `bin_link_geo` builtin handler functions, their argument-parsing logic, the stdin-reading helper used by `bsh-inject`, and the `link_geo_print_status`, `link_geo_print_zone`, `link_geo_print_proximity`, `link_geo_print_refresh`, and `link_geo_print_get` stdout-formatting helpers (or renamed equivalents that produce identical stdout per Requirement 3.4), and SHALL route all error reporting through bsh's `zerr`/`zwarnnam` family or `fprintf(stderr, ...)` with the leading `<builtin-name>:` prefix as in the pre-migration module.
8. THE line count of `Src/Modules/brightlink.c` SHALL NOT be a rejection criterion on its own. As an informational target only, the file SHOULD contain no more than 600 non-blank, non-comment source lines (measured by `cloc --quiet --csv --include-lang=C Src/Modules/brightlink.c` under the `code` column); the migration commit message SHOULD note the architectural reason when the file exceeds that target. The actual gates are criteria 1–7 — a module that passes all of them but lands at, say, 720 lines is a passing migration whose extra lines simply get explained in the commit message.

### Requirement 5: Session Lifetime and Handle Management

**User Story:** As a bsh user invoking `bsh-inject` and `link-geo` repeatedly within a single shell session, I want a single bridge connection and a single registered LINK_REGISTER session to be reused across all calls in that shell, so that I do not pay a fresh handshake on every invocation and the bridge's audit log shows one session per shell rather than one per builtin call.

#### Acceptance Criteria

1. THE migrated_bsh_brightlink_module SHALL hold exactly one `bl_client_t *` in module-global file-scope `static` storage, named `bsh_link_client_g`, and SHALL declare no other `bl_client_t *` globals.
2. THE migrated_bsh_brightlink_module SHALL expose an internal helper with the signature `static bl_client_t *bsh_link_client(void)` that returns `bsh_link_client_g`, allocating it via `bl_client_new()` on the first call when the global is `NULL` and returning the existing pointer on every subsequent call.
3. WHEN a `bsh-inject` or `link-geo` builtin is invoked AND `bsh_link_client_g` is `NULL`, THE migrated_bsh_brightlink_module SHALL invoke `bsh_link_client()` to allocate the client before dispatching the underlying libBrightLink call.
4. WHEN a `bsh-inject` or `link-geo` builtin is invoked AND `bsh_link_client_g` is non-`NULL`, THE migrated_bsh_brightlink_module SHALL reuse the existing client without calling `bl_client_new()` again.
5. IF `bl_client_new()` returns `NULL` during a builtin invocation, THEN THE migrated_bsh_brightlink_module SHALL leave `bsh_link_client_g` as `NULL`, fail only the current builtin invocation with a non-zero exit code and a stderr error message indicating client allocation failure, and SHALL keep the module loaded so that a subsequent builtin call retries the allocation.
6. WHEN the zsh module's `finish_` entry point runs AND `bsh_link_client_g` is non-`NULL`, THE migrated_bsh_brightlink_module SHALL call `bl_client_free(bsh_link_client_g)` and SHALL set `bsh_link_client_g` back to `NULL` before returning.
7. WHEN the zsh module's `finish_` entry point runs AND `bsh_link_client_g` is already `NULL`, THE migrated_bsh_brightlink_module SHALL return success without calling `bl_client_free()`, so that `zmodload` of a module that was loaded but never had a builtin invoked, and a second `finish_` after `zmodload -u`, are both safe.
8. WHEN the zsh module is reloaded via `zmodload -u bsh/brightlink` followed by `zmodload bsh/brightlink`, THE migrated_bsh_brightlink_module SHALL behave on the next builtin invocation as if freshly loaded, allocating a new `bl_client_t` via `bsh_link_client()` with no state carried over from the previous load.
9. WHEN the zsh module's `cleanup_` entry point runs before `finish_`, THE migrated_bsh_brightlink_module SHALL leave `bsh_link_client_g` untouched.
10. WHEN constructing the `bl_client_t`, THE migrated_bsh_brightlink_module SHALL populate `bl_client_config_t` with `agent_name = "bsh"`, `agent_version = ZSH_VERSION`, `socket_path = NULL` so that libBrightLink resolves the bridge socket from `$BRIGHTNEXUS_SOCKET` or its documented default, and `ttl_seconds = 0` to request the library's default session TTL.
11. WHERE the environment variable `BRIGHTLINK_DEBUG` is set to a non-empty value at the moment `bsh_link_client()` allocates the client, THE migrated_bsh_brightlink_module SHALL set `bl_client_config_t.debug_stream = stderr`; otherwise THE migrated_bsh_brightlink_module SHALL set `bl_client_config_t.debug_stream = NULL`.
12. THE migrated_bsh_brightlink_module SHALL assume a single-threaded zsh execution model and SHALL perform no locking around access to `bsh_link_client_g`, with the assumption documented in a comment above the global's declaration.
13. WHEN libBrightLink returns `BL_ERR_NOT_REGISTERED` for any verb call, THE migrated_bsh_brightlink_module SHALL rely on libBrightLink's lazy re-registration rather than retrying explicitly itself.

### Requirement 6: Pin Storage Policy

**User Story:** As a bsh user running an interactive shell, I want my BrightNexus bridge SEP-pin to live for exactly the lifetime of the shell process, so that I get TOFU continuity across builtin invocations within a session without leaving pin state on disk to manage between sessions.

#### Acceptance Criteria

1. THE migrated_bsh_brightlink_module SHALL construct its `bl_client_t` with a `bl_pin_store_t` produced by `bl_pin_store_memory()` as the sole permitted pin-store constructor, so that pin material lives only in process memory for the lifetime of that `bl_client_t` (deliberate trade-off: bsh is a long-lived interactive shell, not a short-lived single-shot tool, and chooses memory-only TOFU continuity over cross-session persistence).
2. THE migrated_bsh_brightlink_module SHALL NOT call `bl_pin_store_file()` with any argument vector, and SHALL NOT call `bl_pin_store_custom()` with a vtable whose `save` callback writes pin material to any on-disk location, so that no libBrightLink-mediated code path writes the pin to disk (rationale: the memory-only policy is enforceable only if every pin-store constructor that can persist is forbidden).
3. THE migrated_bsh_brightlink_module SHALL NOT contain any direct `fopen`, `open`, `write`, `pwrite`, `writev`, or equivalent filesystem-write call that targets the 65-byte uncompressed P-256 pin material outside libBrightLink, and SHALL NOT read or write any SEP-pin file under `$HOME`, `$XDG_DATA_HOME`, `$XDG_STATE_HOME`, `$XDG_CACHE_HOME`, `/tmp`, or any other on-disk location (rationale: prohibiting only the library API is insufficient if module code can side-channel pin bytes to disk itself).
4. THE migrated_bsh_brightlink_module SHALL NOT set `bl_client_config_v2_t.pin_store_borrowed`, so that `bl_client_free()` releases the pin store as part of shell shutdown and the pin material is zeroed from memory at process exit (rationale: lifetime of pin material must be tied to lifetime of `bl_client_t`, with no leakage past `bl_client_free()`).
5. WHEN the bsh process exits by any means (normal exit, signal, `exec`-based shell replacement), THE migrated_bsh_brightlink_module SHALL leave no SEP-pin material on disk that was created by bsh or by libBrightLink on bsh's behalf during the shell's lifetime (rationale: this is the externally observable consequence of the memory-only policy and is the criterion testers verify by inspecting the filesystem after shell exit).
6. WHEN the `bsh/brightlink` module is unloaded via `zmodload -u` and subsequently reloaded via `zmodload`, THE migrated_bsh_brightlink_module SHALL construct a fresh memory-backed pin store with no pin entries carried over from the previous load, causing the next bridge handshake to perform a fresh TOFU prompt (deliberate trade-off, not a bug: memory-only storage means pin continuity is bounded by `bl_client_t` lifetime, which `zmodload -u` ends).
7. WHEN the bsh shell process is replaced via `exec` (including `exec bsh`, `exec` of any other binary, or shell-internal `exec` builtin invocations that replace the process image), THE migrated_bsh_brightlink_module in the replacement process SHALL start with an empty memory-backed pin store and SHALL perform a fresh TOFU prompt on its next bridge handshake (deliberate trade-off, not a bug: process-image replacement discards all in-memory state by definition, and the memory-only policy makes no provision for surviving `exec`).

### Requirement 7: Test-Harness Continuity

**User Story:** As a bsh maintainer landing the migration, I want every test in `bsh/test-harness/` that passed before the change to keep passing after the change, so that I have an objective signal that the migration preserved both the user-visible builtin surface and the on-the-wire BrightLink Protocol behavior.

#### Acceptance Criteria

1. WHEN the test-harness `against-real-brightnexus` suite (invoked via `yarn test:against-real-brightnexus`) is run against a `bsh` binary built from the migrated module's commit, THE test_harness SHALL report a `passed` result for every test that reported `passed` against the pre-migration baseline `bsh` binary, with no test transitioning from `passed` to `failed`, `skipped`, or `todo`.
2. WHEN the test-harness `against-real-bsh` suite (invoked via `yarn test:against-real-bsh`) is run against a `bsh` binary built from the migrated module's commit, THE test_harness SHALL report a `passed` result for every test that reported `passed` against the pre-migration baseline `bsh` binary, with no test transitioning from `passed` to `failed`, `skipped`, or `todo`.
3. WHEN the test-harness `against-real-client` suite (invoked via `yarn test:against-real-client`) is run with a `bsh` binary built from the migrated module's commit, THE test_harness SHALL report a `passed` result for every test that reported `passed` against the pre-migration baseline.
4. WHEN the test-harness `unit` suite (invoked via `yarn test:unit`) is run on the migrated module's commit, THE test_harness SHALL report a `passed` result for every test that reported `passed` against the pre-migration baseline, regardless of whether the unit-level mock seam moved from a Unix-domain-socket mock to a `bl_client_t` mock as part of the migration.
5. WHILE the unit suite's mock seam is being rewired from a socket-level mock to a `bl_client_t`-level mock, THE migration_pull_request SHALL keep each rewired test's user-facing assertions (the values asserted against `bsh-inject` and `link-geo` stdout, stderr, and exit codes, and the §4.5/§4.6/§9 wire-shape assertions) byte-for-byte identical to the pre-migration assertions, with changes confined to test setup and mock construction.
6. THE migration_pull_request SHALL capture the pre-migration baseline as a vitest JSON reporter output (one file per suite) produced by running each of the four suites against the commit immediately preceding the `Src/Modules/brightlink.c` rewrite commit identified in Requirement 8, and SHALL commit those four baseline files to the migration branch before the rewrite commit lands.
7. THE migration_pull_request SHALL NOT introduce any of `it.skip`, `test.skip`, `describe.skip`, `it.todo`, `test.todo`, `it.skipIf`, `test.skipIf`, `it.runIf` (used to disable a previously-running test), `xit`, `xdescribe`, `xfail`, or any equivalent vitest skip/todo marker on a test that did not already carry that marker pre-migration.
8. IF a pre-migration test-harness test asserts on an internal symbol, type, or function from `Src/Modules/brightlink.c` that the migration eliminates, THEN THE migration_pull_request SHALL re-express that test as an assertion on the §4.5/§4.6/§9/§10 protocol surface or on the `bsh-inject` / `link-geo` builtin surface, and SHALL NOT skip, delete, or `todo`-mark it.
9. WHEN `yarn install --immutable` followed by `yarn test` is run from a fresh checkout of the migration branch's tip in an empty directory with the migrated `bsh` binary on `PATH`, THE test_harness SHALL exit with status `0` and SHALL run every test that ran on the pre-migration baseline.
10. IF a pre-migration test-harness expectation is incorrect with respect to BrightLink Protocol §4.5/§4.6/§9/§10, THEN THE migration_pull_request SHALL include a separate commit, preceding the rewrite commit, that fixes that expectation independently and updates the baseline files from criterion 6 in the same commit.

### Requirement 8: Migration Sequence and Reversibility

**User Story:** As a bsh maintainer reviewing the migration as a series of commits, I want each step to be independently buildable and testable, so that I can bisect any regression and so that I can revert just the swap commit if libBrightLink turns out to need fixes without losing the v0.2 surface work.

#### Acceptance Criteria

1. THE migration_history SHALL push the `v0.2.0` annotated tag to the upstream `Digital-Defiance/libbrightlink` repository before any commit referencing the v0.2 surface lands on `bsh/main`, where the tagged commit SHALL satisfy every acceptance criterion in Requirement 1.
2. THE migration_history on `bsh/main` SHALL land the migration as the following ordered commits, each building cleanly and each passing the test-harness suites named in Requirement 7 (criteria 1–4) on its own: (a) submodule-add commit that introduces `subprojects/libbrightlink/` pinned to a commit reachable from the upstream `v0.2.0` tag, with no other source changes; (b) build-system wiring commit that adds the autoconf changes specified in Requirement 2 (criteria 2–9), with `Src/Modules/brightlink.c` still using its pre-migration in-module protocol implementation; (c) the `Src/Modules/brightlink.c` rewrite commit specified in criterion 5 below; (d) optionally, a trailing cleanup commit removing any pre-migration helpers, comments, or unused configure.ac fragments that the rewrite did not need to touch.
3. THE migration_history SHALL ensure that every commit listed in criterion 2 builds cleanly via the project's standard `./configure && make` sequence on macOS and on Debian, and that every such commit passes `yarn test` against the test-harness with status `0`.
4. THE migration_history SHALL pin the `subprojects/libbrightlink/` gitlink in commit (2a) to the exact 40-character commit SHA that the upstream `v0.2.0` annotated tag pushed under criterion 1 points at, and SHALL reject any pin that points at a different SHA even if that SHA is reachable from the tag.
5. THE rewrite commit (2c) SHALL modify only the file `Src/Modules/brightlink.c` and its zsh-build-generated companion files (`Src/Modules/brightlink.epro`, `Src/Modules/brightlink.mdh`, `Src/Modules/brightlink.mdhi`, `Src/Modules/brightlink.mdhs`, `Src/Modules/brightlink.pro`, `Src/Modules/brightlink.syms`), and SHALL NOT touch `configure.ac`, the `.gitmodules` file, the `subprojects/libbrightlink/` submodule pointer, or any test-harness file.
6. THE migration_history SHALL keep every commit listed in criterion 2 reachable from `bsh/main` after merge with no force-pushes, squashes, rebases, or amending that erase any of those commits or the pre-migration `Src/Modules/brightlink.c` content from the reachable history at commit (2c)'s parent.
7. THE migration pull request description SHALL document a one-command revert path of the form `git revert <SHA-of-rewrite-commit>` that returns `Src/Modules/brightlink.c` to its pre-migration content while leaving the submodule and build-system wiring in place, and SHALL state that the same revert continues to build cleanly and pass the test-harness because the submodule-add and build-system commits are independent of the rewrite.
